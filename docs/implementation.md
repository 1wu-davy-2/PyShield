# PyShield 实现思路

本文说明 PyShield 的核心实现：构建期如何加密 Python 模块，运行期如何校验许可证并还原执行，以及为什么在 Pyarmor 的方案上做了取舍。

## 1. 目标与边界

目标：

- 发布目录中不出现可读的 Python 业务源码；
- 保持 CPython 与 Django 的正常行为：导入、反射、模板、ORM、URL 路由、管理命令；
- 支持离线许可证、到期时间、宽限期、签发日期与机器绑定；
- 检测现场对受保护文件与 runtime 的未授权修改；
- 构建与部署流程可重复、可验证。

非目标：

- 绝对不可破解的 DRM；
- 在线激活、试用限制、反调试；
- 对模板、前端资源或数据库加密。

## 2. 组件划分

| 组件 | 职责 |
| --- | --- |
| `shield.py` | 命令行入口：build / issue / verify / inspect / fingerprint / selftest |

| `pyshield/fingerprint.py` | 跨平台机器指纹 |
| `pyshield/tool_license.py` | 构建器自身的工具授权：验签、配额、试用策略（`trial_policy`）与错误码 |

## 3. 构建流程

```text
目标项目 ──发现模块──> compile ──marshal──> zlib
                                            │
                         module_key ── AEAD seal
                                            │
                                       Base85 编码
                                            │
                                  写入 stub（替换原 .py）
```

### 3.1 模块发现

- 项目根必须存在 `manage.py`；
- 根目录下带 `__init__.py` 的目录视为包，递归收集其中的 `.py`；
- 模块 id 由相对路径推导：`blog/views.py → blog.views`，`blog/__init__.py → blog`，`manage.py → manage`；
- 默认排除 `migrations`、`tests`、常见测试文件名，以及 `local_settings.py` / `settings_local.py`（现场配置保持明文）；
- 复制阶段忽略 `.git`、虚拟环境、`__pycache__`、`node_modules`、`staticfiles`、`db.sqlite3`、`.pyc/.pyo`、日志和旧许可证；
- `.pyd`/`.so` 等二进制扩展原样复制，模板、静态资源、JSON 等数据文件原样复制。

### 3.2 生成密文

对每个模块：

1. 以 POSIX 相对路径作为 `co_filename` 调用 `compile(source, filename, "exec", dont_inherit=True)`；
2. 使用 `marshal.dumps` 序列化 code object；
3. 使用 `zlib.compress(level=9)` 压缩；
4. 按模块 id 派生模块密钥，把压缩后的字节封装为 AEAD 信封，AAD 同时绑定 `build_id` 与模块 id；
5. 对信封做 Base85 编码，写入只有加载调用的 stub。

stub 的结构：

```python
# PyShield protected module. Generated by pyshield; do not edit.

from _shield_runtime import load_module as _pyshield_load_module

_pyshield_load_module(
    __name__,
    __file__,
    (
        "P*Yej0RapU...Base85 密文..."
    ),
    'blog.views',
)
```

### 3.3 安装 runtime 与许可证

- runtime 源码（`_shield_runtime/*`、`crypto.py`、`fingerprint.py`、`ed25519.py`、`secure_store.py`）打包在构建器内的 `pyshield/_runtime_bundle.py` 压缩资源中，不再作为 PyInstaller 明文 `datas` 随 `PyShieldBuilder.exe` 发布；构建时解包并写出 `_crypto.py`、`_machine.py`、`_ed25519.py`、`_secure_store.py`；
- 把占位符替换为构建 ID、Ed25519 公钥、算法和 Python 小版本；不再在 `_core.py` 中写入主密钥；
- 生成 `_keyring.py`：把 32 字节主密钥拆成 8 段，与随机掩码 XOR 后以十六进制保存；runtime 通过 `_keyring.master_key()` 重建。构建前会扫描 runtime 目录，若发现完整 Base85/原始/hex 主密钥则拒绝发布；
- Trial 默认 `pyc`：把 runtime 编译为 `UNCHECKED_HASH` 的 `.pyc` 并删除 `.py`，不发布 runtime 源码；
- Pro/Enterprise 在工具链可用时默认 `--runtime-native`：用 Cython 把 `_core`、`_crypto`、`_ed25519`、`_chacha_fast`、`_keyring` 编译为 `.pyd`/`.so` 并删除对应 `.py`。构建机需要 Cython、setuptools、C 编译器以及 strip/llvm-strip；Windows 上会自动探测 MinGW-w64，也可用 `MINGW_PREFIX` 指定。构建后执行 `strip --strip-unneeded`、删除 `.pdb/.ilk/.exp/.lib` 并清 PE CodeView；strip 失败会终止构建。原生扩展与操作系统、CPU 架构和 Python ABI 绑定，必须在与部署机一致的环境中构建；
- `--runtime-source` 仅用于调试：保留 `.py` 源码并明确警告会暴露解密逻辑；`--runtime-native` 与 `--runtime-pyc` / `--runtime-source` 互斥；`_chacha_fast.pyx` 在安装结束后删除；
- 构建时生成 32 字节 Ed25519 签名私钥，公钥写入 runtime；私钥只保存于构建密钥；
- 由 `master_key` 和 `build_id` 通过 HKDF 派生 32 字节 `build_key`；模块用它加密，但 `build_key` 不再写入 `pyshield.lic`。许可证格式 v3 只承载授权字段，先签名再用 `master_key` 派生出的许可证密钥加密；
- 生成并签名 `.pyshield-manifest.json`：默认登记 stub（`code`）与 `_shield_runtime/`（`runtime`），`full` 模式再登记模板与数据文件（`data`）；许可证、本地配置、数据库、日志、媒体、staticfiles 等可变文件不登记；
- 构建密钥另行写入输出目录同级的 `*.shield-secret.json`（格式 3），记录 `master_key`、派生出的 `build_key`、`signing_key`、`integrity`、`manifest` 路径与 `grace_days`，用于后续重新签发与复核；
- 写入 `.pyshield-build.json` 标记（含 `runtime` 与 `integrity`），并默认在产物上运行 `manage.py check`。

## 4. 密钥体系与信封

### 4.1 密钥派生

```text
构建时生成：
  master_key（内嵌 runtime）
     ├─ HKDF(salt="pyshield-build-key-v1", info=build_id)
     │    ▼
     │  build_key（模块加密密钥，不写入许可证）
     │    └─ HKDF(salt=SHA256("pyshield-module-v1" + module_id),
     │            info="pyshield-module-key")
     │         ▼
     │      module_key
     │         └─ HKDF(salt="pyshield-envelope-v1",
     │                 info="encryption", length=64)
     │              ├── 32 B 加密密钥
     │              └── 32 B MAC 密钥
     └─ HKDF(salt="pyshield-license-v3", info=build_id)
          ▼
       license_key ──> pyshield.lic（仅授权字段，载荷由 signing_key 签名）

  signing_key（只留在构建方）──签名──> pyshield.lic
  signing_public_key（内嵌 runtime）──验签──> 拒绝伪造或篡改的许可证
```

每个模块使用独立密钥，互相不可替换；`build_key` 不直接出现在模块文件中，也**不再出现在许可证里**。格式 3 的许可证只承载到期、绑定、客户等授权信息；模块密钥由 runtime 从主密钥本地派生。旧格式 2 许可证仍可被构建侧读取，用于已有构建的续期，但新构建一律生成格式 3。

### 4.2 信封格式

```text
MAGIC "PSX1"      4 B
version           1 B
cipher id         1 B   (1=AES-GCM, 2=ChaCha20+HMAC, 3=ChaCha20-Poly1305)
nonce_len         1 B   (固定 12)
tag_len           1 B   (16 或 32)
nonce            12 B
ciphertext        N B
tag           16/32 B

AAD = 头部 8 字节 + "pyshield-module:<build_id>:<module_id>"
```

- **AES-256-GCM**（id 1）：`cryptography` 可用时使用，16 字节 tag；
- **ChaCha20 + HMAC-SHA256**（id 2）：纯 Python 实现，加密后对“头部 + AAD + 密文”做 HMAC，32 字节 tag，属于 encrypt-then-MAC；若 runtime 中编译了 `_chacha_fast`，ChaCha20 部分走原生实现，帧格式不变；
- **ChaCha20-Poly1305**（id 3）：`cryptography` 可用时使用，16 字节 tag，适合没有 AES 硬件加速的平台；
- `--cipher` 的 `auto` 选择 AES-GCM（无 `cryptography` 时退回纯 ChaCha），`chacha` 优先 ChaCha20-Poly1305，`chacha-pure` 强制纯 ChaCha，`aesgcm` 强制 AES-GCM；
- 解封前先验证认证标签，失败统一抛出“invalid or corrupted data”，不暴露内部原因；
- nonce 每次随机生成；AAD 绑定 `build_id` 与模块 id，既防止把 A 模块的密文移植到 B 模块，也防止把一个构建的密文移植到另一个构建。

### 4.3 完整性清单

清单格式 1，文件名 `.pyshield-manifest.json`。签名对象是去掉 `signature` 后的规范 JSON，前缀为 `pyshield-manifest-v1:`；文件内容形如：

```json
{
  "format": 1,
  "build_id": "674e218b99ac24c5",
  "cipher": "chacha20poly1305",
  "integrity": "protected",
  "files": {
    "manage.py": {"sha256": "…", "size": 123, "category": "code"},
    "_shield_runtime/_core.py": {"sha256": "…", "size": 456, "category": "runtime"},
    "app/templates/page.html": {"sha256": "…", "size": 78, "category": "data"}
  }
}
```

构建期分类规则：

- 实际加密的模块 stub 记为 `code`；
- `_shield_runtime/` 下的文件记为 `runtime`；
- 其余数据文件记为 `data`；
- 默认可变模式（许可证、本地配置、`.env`、数据库、日志、`media/`、`staticfiles/` 等）与 `--mutable` 额外模式不登记；`__pycache__`/`.pyc` 不是可变文件：清单生成阶段直接拒绝带缓存的树，构建结束也会清理并断言。

runtime 在加载首个受保护模块前用内置公钥验签，再按模式校验 `code` + `runtime`（`full` 模式再加 `data`）：路径必须安全、文件必须存在、大小与 SHA-256 必须一致。新增文件不报错，登记文件缺失或被修改即拒绝加载。清单在临时输出目录中生成，不包含自身、许可证与构建标记。

## 5. 运行时加载

`load_module()` 的流程：

1. 校验运行环境为目标 CPython 小版本；
2. 读取 `.pyshield-manifest.json`，校验格式、`build_id`、算法、完整性模式与 Ed25519 签名；
3. 按模式计算 `code`、`runtime`（以及 `full` 模式下的 `data`）文件的 SHA-256；
4. 读取许可证：`PYSHELD_LICENSE` → `manage.py` 同目录 → runtime 包内；
5. 用 `master_key` 派生许可证密钥并解封，校验 `format == 3`；再用内置的 Ed25519 公钥验证载荷签名（域前缀 `pyshield-license-v3:`），签名无效立即拒绝，之后的字段一律不信任；
6. 校验 `build_id`，从 `master_key` 和 `build_id` 派生 `build_key`（许可证里没有该字段）；
7. 读取时钟状态：主文件 + 独立锚点（默认在 `~/.pyshield/` 与平台状态目录，可用 `PYSHELD_STATE_DIR` / `PYSHELD_STATE_ANCHOR_DIR` 覆盖）。Windows 用 DPAPI 封装，其它平台用 HMAC，MAC 密钥由 `build_key` 派生；缺失一份会从另一份恢复；两份日期不一致时取较新值并重写两份，避免部分写入失败造成永久拒绝启动；旧公开-MAC 状态兼容读取一次后自动迁移。今天早于 `last_seen` 超过 1 天即判定时钟回拨；两份都不可写且未设置 `PYSHELD_ALLOW_VOLATILE_STATE=1` 时拒绝启动；
8. 校验 `not_before`（允许 1 天误差）、到期日与宽限期（`expires + grace_days` 之前放行，宽限期内标记 `in_grace`）以及机器指纹；首次启动绑定同时检查主记录与位于 `_shield_runtime/` 的锚点，删除主记录不会重置绑定；
9. 按模块 id 派生模块密钥，用绑定 `build_id + module_id` 的 AAD 解封模块信封；
10. `zlib.decompress` → `marshal.loads`；中间缓冲使用 `bytearray`，解包后立即覆写清零（降低 dump 窗口，但不能让 code object 消失）；
11. 递归替换 code object 及其嵌套 code 的 `co_filename`，让 traceback 指向部署路径；
12. 保留原模块对象上的 `__package__`、`__path__`、`__spec__`，把解出的代码 `exec` 到模块命名空间。

即使攻击者从 runtime 中提取了对称主密钥，也只能解密许可证、无法生成新的有效签名；修改到期日、机器指纹或绑定信息都会导致验签失败。许可证、清单与时钟状态在首次校验后缓存，并用锁避免并发重复校验；`load_module()` 每 5 分钟触发一次重新校验，避免长期运行的进程跨过到期日。`reload_license()` / `license_status(refresh=True)` 会清空缓存并重新校验，便于替换续期后的许可证；**清单校验结果独立缓存且只在进程首次加载时扫描一次**，不随许可证刷新重新计算哈希，因此 5 分钟重验不覆盖完整性。

任何一步失败都会抛出 `ImportError` / `LicenseError`，模块不会以明文形式落地。`python -m _shield_runtime status|verify` 复用同一套校验逻辑，供现场部署检查。

## 6. 许可证与指纹

许可证载荷（签名并加密前）包含：

```json
{
  "format": 3,
  "build_id": "16 位十六进制",
  "cipher": "chacha20poly1305",
  "python": "3.12",
  "created": "2026-11-12T...",
  "not_before": "2026-11-13",
  "expires": "2027-12-31 或 null",
  "grace_days": 14,
  "bind_mode": "first-run",
  "fingerprints": ["..."],
  "customer": "客户名称",
  "signature": "Base85 Ed25519 签名"
}
```

签名对象是“去掉 `signature` 后的载荷按 key 排序、无空白的紧凑 JSON”，前面加上域前缀 `pyshield-license-v3:`；签名值本身再放入载荷，最后整体用 AEAD 加密。`signing_key` 只在构建方保存，runtime 仅嵌入 `signing_public_key`。格式 3 的载荷**没有 `build_key`**；构建方从构建密钥中的 `master_key + build_id` 派生，runtime 同样派生。旧格式 2 的许可证仍可读取（使用 `pyshield-license-v2:` 前缀与旧盐），用于已有构建的续期；新构建一律生成格式 3。

构建密钥 `*.shield-secret.json`（格式 3）保存 `master_key`、派生出的 `build_key`、`signing_key`、`signing_public_key`、构建 ID、算法、`integrity`、`manifest`、`grace_days`、Python 小版本、产物与许可证路径；`issue` 读取这些字段重新签名并重写许可证，不重新加密代码。格式 3 的 `build_key` 必须与 `master_key + build_id` 派生值一致；旧格式（format 1）的许可证和构建密钥都会被拒绝。

时钟状态包含 `format`、`build_id` 和 `last_seen`，用 `secure_store.seal_state` 封装：

- Windows：DPAPI 保护，绑定当前用户/机器；DPAPI 失败时退化为 `PLAIN1`（仍带 HMAC）；
- 其它平台：`PLAIN1` + HMAC-SHA256；
- MAC 密钥由 `build_key` 派生，而不是公开的机器指纹；提取 master key 后仍可伪造；
- 主文件与独立锚点各写一份；删除其中一份会从另一份恢复；两份日期不一致时取较新值并重写两份；写入使用唯一临时文件、共享冲突重试和跨进程锁。旧公开-MAC 状态默认拒绝，只有显式 `PYSHELD_ALLOW_LEGACY_STATE=1` 才允许一次性迁移；未来日期超过 7 天按损坏状态拒绝。两份都不可写时默认拒绝启动，`PYSHELD_ALLOW_VOLATILE_STATE=1` 可显式放弃持久化回拨检测；
- 默认状态按 OS 用户隔离；多用户场景用 `PYSHELD_STATE_ANCHOR_DIR` 指向机器级 ACL 目录。

首次启动绑定的主记录仍在输出目录 `.pyshield-binding.json`，锚点位于 `_shield_runtime/.pyshield-binding.json.anchor`；两者都带 `build_id`、机器指纹、绑定时间与由 `build_key` 派生的 HMAC。读写复用 `secure_store` 的唯一临时文件、共享冲突重试，并在整个 read-modify-write 外层持有跨进程锁；单份写入失败不会阻塞启动，下一次启动会从存活副本恢复。删除主记录会从锚点恢复，删除锚点会从主记录重建；两者同时删除才会被视为首次运行。任何非 onedir `_MEIPASS` 都被视为临时目录并拒绝首次绑定；`PYSHELD_BINDING_FILE` 不会关闭该检查，也不能让 onefile 解压目录持久化，override 路径包含 `_MEI*` 也会被拒绝；应改用固定指纹或 onedir。

机器指纹来源：

- Windows：`HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`，失败时回退卷序列号，再回退主机名与 MAC；
- Linux：`/etc/machine-id` 或 `/var/lib/dbus/machine-id`；
- macOS：`ioreg` 读取 `IOPlatformUUID`；
- 原始值经 SHA-256 后取前 32 位十六进制，避免直接暴露系统标识。

## 7. Django 兼容与设计取舍

Django 大量依赖导入、反射和代码内省，因此 PyShield 刻意避免会改变模块行为的保护手段：

| 保留 | 原因 |
| --- | --- |
| 编译成 code object 后加密 | 不发布源码，同时保持 CPython 语义 |
| 逐模块 AEAD 与独立密钥 | 单模块泄露不影响其他模块，可检测移植 |
| 构建级密钥与离线许可证 | 支持到期、设备绑定、离线重发 |
| Ed25519 许可证签名 | 主密钥泄露也无法伪造或篡改许可证 |
| 签名完整性清单 | 发现受保护文件与 runtime 的现场修改、删除或跨构建移植 |
| 模块 AAD 绑定 `build_id` | 一个构建的密文无法移植到另一个构建 |
| 带 HMAC 的时钟状态 | 检测明显的系统时钟回拨，抬高改时钟绕过到期的成本 |
| 可选 Cython 原生 runtime | 把密钥与验签逻辑藏进二进制，并加速纯 ChaCha 回退 |
| Django 友好的排除规则 | 迁移、模板、静态资源保持可用 |

| 舍弃 | 原因 |
| --- | --- |
| 名称混淆、调用断言、`--restrict` | 破坏 Django 反射、模板和 ORM 内省 |
| 在线注册、试用限制 | 依赖网络，增加部署复杂度 |
| 反调试、反注入 | 维护成本高，收益有限 |
| 预编译跨平台 runtime | 与平台和 Python ABI 强绑定，改为在目标环境用 Cython 现场编译 |

## 8. MCP 构建服务

MCP 是构建引擎之上的本地 agent 适配层，不改变产物格式或 runtime：

| 层 | 职责 |
| --- | --- |
| `pyshield/mcp_server/` | stdlib newline-delimited JSON-RPC 2.0；initialize、tools、resources、prompts、取消与 shutdown |
| `pyshield/mcp_server/http_transport.py` | 把同一分派逻辑暴露为回环 Streamable HTTP：`POST/DELETE /mcp`、`GET /health`、Bearer 令牌、1 MiB 上限 |
| `gui/mcp_host.py` | 桌面端宿主：设置 → `BuildPolicy`、令牌文件、端口顺延、启停、客户端配置片段 |
| `pyshield/build_service/` | `BuildRequestV1`、严格预检、异步 job、失败分类、额度结算、日志/审计 |
| `pyshield/build_spec.py` | 路径/reparse、output_name、expiry/grace/bind/pattern 等纯校验基元 |
| `pyshield/tool_license.py` | 跨进程账本 `begin_build/refund_build/finalize_build`，trial/quota v2（pending/refunded/credits） |
| `pyshield/builder.py` | `ProjectCodeError`、`console_log`、`require_absent_output`、`secret_path`、唯一临时目录 |

关键取舍：

- 构建默认 `no_verify`，不执行目标项目代码；只有 `pyshield_check_output` 在复制出的沙箱中运行 `manage.py check`。
- 预检通过后才扣额度；只有 `PROJECT_CODE` 失败退款；预检失败不扣；取消/超时不退。
- MCP 构建的 secret 写到独立 `--secret-dir`，不在输出目录同级；响应与日志不返回密钥。
- stdout 只写 JSON-RPC；builder 用 `contextvars` 抑制所有构建日志到 stdout，日志进入 per-job 文件和 stderr。
- 传输与协议分派解耦：`JsonRpcServer.handle()` 返回响应列表，stdio 循环负责写帧，HTTP 处理器负责序列化；两种形态工具集与校验完全一致。
- 桌面构建器以 `console=True` + `hide_console="hide-early"` 打包，双击只出窗口，被 MCP 客户端拉起时仍保留 stdin/stdout。
- 额度账本与 pending/refunded 状态一次原子写入，避免“扣了额度但没记幂等”或重复退款；跨月退款进入下月 credit。

### 8.1 工具面

| 工具 | 执行代码 | 扣额度 | 说明 |

### 8.2 额度状态机

| 阶段 | 额度 |
| --- | --- |
| schema/路径/项目树/敏感文件/语法/授权预检失败 | 不扣 |

| 静态校验失败 | 不影响已发生额度 |

## 9. 验证方式

- `python -m unittest discover -s tests -v`：覆盖算法向量、密钥隔离、许可证、构建器结构、stub 可执行与输出目录保护；
- Ed25519 RFC 8032 标准向量，纯 Python 与 `cryptography` 实现交叉一致，篡改签名被拒绝；
- 伪造场景：提取 `master_key`、解密许可证、去掉到期日再重新封装，runtime 仍因签名无效拒绝加载；
- 原生算法：ChaCha20-Poly1305 与 AES-GCM 的往返、AAD 绑定和密文防篡改；native ChaCha 回退与纯 Python 结果逐字节一致；
- 原生 runtime：构建产物包含 `.pyd`/`.so` 且删除对应 `.py`，`--cipher chacha-pure` 产物可正常 `manage.py check`；
- 构建阶段在产物上运行 `manage.py check`；
- 篡改验证：修改受保护文件后加载失败，报“package integrity check failed”；`--integrity off` 时改为密文认证失败；
- 清单验证：签名错误、清单缺失、登记文件大小/哈希变化、跨构建清单均被拒绝；可变文件与新增文件不破坏启动；
- 时钟验证：伪造/损坏 `last_seen` 会因 DPAPI/HMAC 不匹配被拒；时钟早于 `last_seen` 超过 1 天被拒；删除单份状态会从另一份恢复；两份日期不一致会取较新值对齐；旧公开-MAC 状态默认拒绝，需显式开关才能一次性迁移；8 进程并发启动全部成功；宽限期边界与 `not_before` 有单元测试；
- 许可证验证：格式 3 载荷不含 `build_key`；旧格式 2 仍可读取；过期拒绝、宽限期放行、换绑生效、重新签发无需重新构建、热重载生效；
- 安全回归：runtime 压缩资源与源码逐字节一致；PyInstaller spec 不再包含 `runtime_template` 或 `crypto.py` / `fingerprint.py` / `ed25519.py` 明文 datas；默认产物不含 `_core.py`；纯 Python ChaCha 在分块边界与参考实现一致；
- 现场验证：`python -m _shield_runtime verify` 与 `python shield.py verify` 覆盖清单、文件与许可证；
- MCP 验证：stdio 握手、工具 schema 严格拒绝未知字段、路径/reparse 逃逸、并发扣额不超卖、代码错误退款且只退一次、默认不执行项目代码、`check_output` 沙箱、secret 不出现在响应/日志/审计；
- Django 集成验证：模板、静态文件、迁移、ORM 与路由在加密产物中正常工作。

## 10. 已知边界与演进方向

- 服务端代码最终要在内存中解密，runtime 中的 `master_key` 也可能被提取；Ed25519 签名能阻止伪造许可证，但无法阻止攻击者绕过校验逻辑或 dump 已解密的代码。安全强度依赖攻击成本与配套授权手段。
- **离线分发不存在绝对机密性**：格式 3 移除了许可证中的 `build_key`，默认 runtime 也不再发布 `.py`，但主密钥仍在客户机内存/扩展中。需要真正机密性时，应引入服务端解锁（许可证 + 机器指纹 + 短期密钥）、TPM/加密狗，或把密钥拆到独立的原生模块。
- 构建与部署必须使用相同的 Python 小版本；原生 runtime 还要求相同操作系统、CPU 架构和 Python ABI。
- AES-GCM 与 ChaCha20-Poly1305 依赖 `cryptography`；纯 Python ChaCha 零依赖但速度低，`--runtime-native` 会编译 `_chacha_fast` 作为快速回退。
- `--runtime-native` 显著提高静态提取门槛，但 `.pyd`/`.so` 仍可被逆向；它适合提高攻击成本，不适合当作绝对防护。
- 迁移与测试默认不加密；模板与静态资源不加密，前端代码对用户可见。
- 完整性清单由 runtime 自身执行，且只在进程首次加载时扫描一次，不能防御“整体替换 runtime”的攻击；时钟与绑定记录可被同时删除以重置历史。状态 MAC 由 `build_key` 派生，提取 master 后仍可伪造。两者用于抬高成本与发现误改，不是绝对 DRM。
- 发布卫生仍未闭环：`PyShieldBuilder.exe` 需要 Authenticode 证书才能消除“未签名”提示；PyInstaller 内置二进制仍可能带 PDB 路径。详见 [security-hardening.md](security-hardening.md)。
- 可继续演进：服务端首绑登记/解锁、硬件密钥、更强的二进制混淆、模板按需加密、自动化发布暴露审计。
